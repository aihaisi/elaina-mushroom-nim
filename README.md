## 玩法规则

盘子从左到右**依次解锁**——只有最左侧未空的盘子可以取，该盘取空后才能动下一个。

- 每回合至少取 1 个，最多取走当前盘全部
- **取走最后一个蘑菇的人获胜**（正常博弈，非 Misère）

盘面随机生成：盘数 `n ∈ [3,5]`，每盘 `a_i ∈ [1,6]`；其中 `a_i = 1` 按 20% 的概率出现
（比均匀分布高 20%，原因与实测影响见下方「出盘分布」一节）。

---

## 核心：这个游戏的最优解

多数人第一次玩会本能地去数"还剩几个盘子"，但正确的分析维度是**当前盘还剩几个**。

### 结构性质（博弈树归纳可证）

| 局面 | 结论 |
|---|---|
| 当前盘剩余 `m ≥ 2` | **轮到的人必胜** |
| 当前盘剩余 `m == 1` | 没有选择，只能取走；胜负取决于下一盘开局对对手是输是赢 |

为什么 `m ≥ 2` 必胜？因为面对 `m ≥ 2`，你总有两个出口，且至少一个能把败局丢出去：

1. 下一个盘子的**开局对对手是必败态** → 一次取空，把这个必败态递给他
2. 否则 → **只留 1 个**，把对手顶死在"唯一合法步"上

### 闭式解

记 `lose[j] = 「轮到某人从第 j 个盘子开始处理（该盘满额 a[j]）时，他必输」`：

```
lose[n] = true                                   // 盘面已空，无子可取者判负
lose[j] = (a[j] === 1) ? !lose[j + 1] : false    // 盘子 > 1 ⇒ 这里的人握着主动权
```

一次 `O(n)` 递推就能把整局判完，不需要搜索。

### 人能直接用的形式：数「连续 1 蘑菇盘」的奇偶

把上面那条递推展开，得到的是一条不需要写代码、当场就能用的规则。设 `r` = 「从当前位置起，紧随其后的连续『只有 1 个蘑菇』的盘子个数」：

| 局面 | 结论 |
|---|---|
| `a[j] >= 2` | **必胜**（取空 或 只留 1 个，二选一） |
| `a[j] == 1`，且这条 1 链被某个 `>= 2` 的盘截断 | 必败 当且仅当 `r` 为**奇数** |
| `a[j] == 1`，且这条 1 链一直延伸到盘尾 | 必败 当且仅当 `r` 为**偶数** |

> 实战版：面对一个 `>= 2` 的盘，只需要数**后面连着几个"只有 1 个蘑菇"的盘**——奇数就一次取空，偶数就只留 1 个。
> （末尾全为 1 时奇偶反过来，因为"盘面取空判负"把基准翻转了一次。）

这条规则也是本作**"转机"全在 1 蘑菇盘上**的正式解释：那些盘子自己没有任何选择（轮到就只能取走），
却单方面决定了前面某个 `>= 2` 的盘唯一正确的那手走法。

它的等价性由 `verify-ai.mjs` 的 I 节守着：穷举 `n ≤ 6`、`a_i ∈ [1,6]` 的全部 55986 个盘面逐个比对求解器，
外加 20000 个大值域随机盘面。

### 一个反直觉的推论

> **必败态必然是 `m == 1`，而 `m == 1` 时走法唯一。**

所以这个游戏里**不存在"必败时随机挣扎"这种设计**——最优 AI 的每一步都被唯一确定，没有概率、没有个性、没有"偶尔失误让你一局"。

这条推论直接决定了一个设计后果：**玩家一步走错，AI 接管必胜态势，再也不可挽回**。当前出盘分布下先手理论必胜率 **83.52%**——也就是说玩家先手时，走对就赢、错一步就死，而另外 **16.48% 的局开局就是死局**。

## 出盘分布：唯一的调参入口

出盘参数集中在 `index.html` 的 `/* ==== MUSHROOM-SPAWN BEGIN/END ==== */` 块里，只有一个旋钮：

```js
const ONE_MUSHROOM_BOOST = 1.25;   // a_i = 1 的权重倍率（其余点数权重为 1）
const MIN_PLATES = 3, PLATE_SPAN = 3;   // 盘子数 n ∈ [3, 5]
```

`1.25` 解出来的分布：**`P(a_i = 1) = 1.25 / 6.25 = 20%`**，其余五档各 `16%`——即 1 蘑菇盘的出现率比均匀分布（`1/6 ≈ 16.67%`）**高 20%**。

| 指标 | 均匀分布 | 调参后（1.25） |
|---|---|---|
| `P(a_i = 1)` | 16.67% | **20.00%**（基准的 120%） |
| 开盘就含 1 蘑菇盘的局面 | 51.24% | **58.36%** |
| 最长连续 1 蘑菇盘 / 局 | 0.596 | **0.703** |
| 首盘后连续 1 蘑菇盘 / 局 | 0.198 | **0.246** |
| 先手必败率（"看穿认输"能用的局） | 14.17% | **16.48%** |
| 决策点（`m >= 2`）个数 / 局 | 3.333 | 3.200 |
| 平均蘑菇总数 / 局 | 14.00 | 13.60 |

代价只有一格：**决策点从 3.33 降到 3.20（−4%）**。原因是 1 蘑菇盘轮到就没得选，
所以提高它的比例必然小幅稀释"真正要做决定"的次数。换来的是连续 1 蘑菇链变长近 18%——
而链越长，前面那手"取空 / 留 1"的判据越深、越像一道题，越不像送分。

以上数字都是**穷举全部盘面按概率加权精确算出**的（不是抽样估计），
口径与验证器 I 节的断言一致。

## AI 是"可证最优"的，不是"测试过最优的"

`verify-ai.mjs` 一共九层验证，跑一次秒级完成：

| 层 | 内容 | 规模 |
|---|---|---|
| A · 穷举对账 | 闭式解 vs 博弈树暴力 DP，逐状态比对胜负判断 | 1364 盘面 / 15930 个可达状态 |
| B · 走法正确性 | 每个必胜步必须把对手送进必败态 | 其中 9558 个真正需要抉择的 `m ≥ 2` 局面 |
| C · 必败态唯一性 | 守住"`m == 1` 才可能必败"这条定理 | 同上 |
| D · 经典判据交叉核对 | 与"前导 1 的个数"判据等价性验证 | 全部盘面 |
| E · 大值域自对弈 | 双方均走最优，终局胜者必须等于开局裁决 | 2000 局（`n ≤ 50`、`a_i ≤ 1e6`） |
| F · 认输门控流程 | DOM 桩驱动真实页面脚本，验证门控与结算 | 13 条断言 |
| G · **官方样例对拍** | 与题面给出的期望输出逐个比对 | 5/5 |
| H · 发布副本一致性 | `site/index.html` 必须与根 `index.html` 逐字节一致 | 1 条断言 |
| I · 出盘分布与「1 蘑菇转机」 | ① 可读奇偶规则 vs 求解器等价性；② `P(a_i = 1)` 必须确为 20% | 55986 盘面穷举 + 20000 大值域随机 + 出盘概率穷举 rand 网格 |

两个容易做错的关键点：

**① 验证器不抄副本，直接从 `index.html` 里抽代码。**
求解器被显式标记在 `/* ==== MUSHROOM-SOLVER BEGIN/END ==== */` 之间，验证脚本把这整块抽出来 `new Function` 执行。测的就是真正跑在页面上的那份代码——避免"测的是副本、上的是另一版"这种经典事故。

**② G 层是唯一的"外部权威"校验。**
A~E 全都是跟"我自己写的暴力解"对账——万一我对规则的整体理解就是偏的，两边会一起错。只有题面官方样例是出题人给的独立答案，所以它单独占一层。

**③ 概率类断言穷举 rand，不做统计抽样。**
I 节要断言"`a_i = 1` 的出现率是 20%"，如果靠抽 10 万次随机数去估，抽样方差会让它偶发失败——
**一个会随机变红的断言等于没有断言**。所以出盘抽样器被写成纯函数 `pickPlateCount(rand)`（随机数由外部传入），
验证器直接在 `[0,1)` 上扫一遍网格，把分布精确算出来。

此外还做过**两轮变异测试**，确认断言真的会失败：

- **求解器/流程侧**：注入 6 个真实缺陷（删掉 `m ≥ 2` 判定、把取空/留 1 的分支对调、改错 `lose` 递推方向等），抓到 4 个；
  另 2 个逃逸经论证属于**等价变异**（行为保持不变），不是断言缺口。历史上真实出现过的"双重 bug"（守卫 + 置位顺序）完整复原后**被抓到**。
- **出盘分布侧**：注入 6 个缺陷（把倍率调回 1.0、调过头到 1.5、权重表忽略倍率、上界写错、丢掉 `lose` 的取反、盘子数上界改小），
  **6/6 全部被抓到**。这一轮还真抓出一处**断言自身的缺陷**：最早我把盘子数取值域写成"和 `MIN_PLATES`/`PLATE_SPAN` 自洽"，
  那是个恒真式——把上界从 3 悄悄改成 2 照样通过。改成钉死字面量 `[3, 4, 5]` 后才真正生效。
  同理，报告行里曾写死过一句 `✓ 与求解器完全一致`，断言失败时它仍然打印 ✓；
  **一份永远显示成功的报告比没有报告更糟**，现已改为由真实结果驱动。

## 特色机制：看穿认输

因为存在"开局即必败"的死局，原型加了一条非常规规则作为平衡器：

> 在你走出第一步之前，可以点【认输】声明"我看穿了"。
> **判对算你赢，判错算你输**；只要走过任意一步，认输资格就永久作废。

这条机制的设计要点：

- **两条路都通向"你必须真的理解局面"**：看懂死局 → 认输拿分；误判必胜局 → 认输直接输掉。猜错要付代价，否则"无脑点认输"就成了最优策略。
- **按钮文案严格中性**。早期版本会随裁决变色变字（`认输（看穿败局）` 紫色 / `认输（放弃胜利）` 橙色）——那样按钮本身就成了**答案播报器**，玩家不用思考，看一眼按钮就知道自己是不是必败局。现在必胜局与必败局显示完全一致，这条被 `verify-ai.mjs` 的 F 层用断言钉死。

## 项目结构

```
elaina-mushroom-nim/
├── index.html       # 全部内容：样式 + 求解器 + UI 逻辑（单文件，零依赖）
├── site/
│   └── index.html   # 线上发布副本（必须与根文件逐字节一致，H 层断言守）
├── verify-ai.mjs    # 穷举/自对弈/流程/官方样例 验证器（Node，无 npm 依赖）
├── README.md
└── LICENSE          # MIT
```

> **为什么发布的是 `site/` 而不是项目根目录**：根目录还放着 `.workbuddy/`（项目记忆）等开发侧文件，
> 直接发布它们会变成公开可下载的 URL。`site/` 里只有游戏本体这一个文件。
> 改完 `index.html` 记得同步：`cp index.html site/index.html`——忘了的话 H 层断言会直接失败。

`index.html` 内部划分：

| 区块 | 职责 |
|---|---|
| `MUSHROOM-SOLVER` 标记块 | `computeLosingFlags` + `analyzePosition`，博弈论核心 |
| `MUSHROOM-SPAWN` 标记块 | 出盘分布（`ONE_MUSHROOM_BOOST` 等调参入口）+ 纯函数抽样器 |
| `aiTurn()` | 调用求解器执行最优走法 |
| `playerSurrender()` / `openingIsLosing()` | 看穿认输的判定与结算 |
| `renderBoard()` 等 | 渲染与交互 |

**AI 与玩家侧判定共用同一个 `analyzePosition`**——这是刻意的：历史上两者曾各写一套判据，导致 AI 按最优走而认输按钮给出相反裁决。

## 一个值得记下来的坑

"看穿败局 → 判胜"这个分支，第一版是**死代码**：

```js
isGameOver = true;              // ← 先置位
if (isPlayerLosing()) { ... }   // ← 而该函数自带 isGameOver 守卫 → 恒返回 false
```

不管你多准地看穿必败局，点了认输永远被判负。修法是双保险：判定函数改成**纯位置查询、不带任何外部状态守卫**，同时把判定提到置位之前。只改一处，下次还会被人改回去。
